# 前端需求文件:國小智慧排課系統

> 本文件定義前端的目標、範圍、頁面清單、技術選型與使用者流程,是下一個 Task(建立 React 專案骨架)開始前的規格依據。本文件本身不包含任何程式碼、不建立任何 React 專案檔案。

---

## 1. 目標與範圍原則

目前系統只能透過 Swagger UI 操作。對非技術背景的人,甚至對只有短時間評估這個專案的技術面試官來說,這種操作方式在體驗上等於沒有介面——所有的排課邏輯、Explainable Scheduling、靜態可行性檢查,全部埋在 JSON 回應裡,沒有人會在幾分鐘內感受到這些設計的價值。

前端存在的目的,是**降低理解門檻**,不是做一套完整的教務系統。這個定位決定了每一個功能要不要做的判斷標準:

> 任何一個畫面,先問:「這個畫面能不能讓看的人在 10 秒內感受到『這是一個會思考的排課系統,不是一個表單工具』?」
>
> 不能的,不做。

這條原則貫穿第 2 章的頁面取捨與第 3 章的排除清單——例如「失敗診斷畫面」直接把系統最花力氣打磨的 Explainable Scheduling 攤開來給人看,所以是優先順序最高的頁面。

### 分階段策略

這個系統最終的目標,是讓**教務處人員**親自上手日常操作,而教務處人員不會使用 Swagger UI。這代表完整的資料操作能力不是「不做」,而是「現在資源有限,先延後,但一定要做,而且要盡快能加回來」。因此採用分階段策略:

- **階段 A(現在立即要做)**:第 2 章列出的 6 個頁面,唯讀為主,聚焦展示排課引擎的核心能力。本文件第 2、5、6 章描述的範圍都屬於階段 A。
- **階段 B(之後,有餘裕再做)**:教務處日常操作所需的完整 CRUD 表單與使用者/角色管理介面,詳見第 7 章。

**階段 A 開發時,必須保留往階段 B 擴充的空間,不能把架構寫死成純唯讀。** 這不是「先求有再求好」的建議,而是第 4 章列為硬性約束的技術要求——如果階段 A 自我限縮成純唯讀架構,階段 B 動手時就等於要重寫階段 A 的程式碼。

## 2. MVP 頁面清單

| 頁面 | 目的 | 對應後端 endpoint |
|---|---|---|
| 登入 | JWT 認證,取得 token | `POST /api/v1/auth/login` |
| 基礎資料瀏覽(唯讀為主) | 讓使用者看到系統裡有哪些老師/班級/科目/教室/時段,建立情境感,不是完整 CRUD。採單頁 + 分頁籤切換(不做成獨立路由的多個頁面),理由:資料類別只有 4–5 個,分頁籤在展示情境下資訊一目瞭然、開發成本較低,且此頁定位是「輕量瀏覽」而非長期日常操作工具 | `GET /api/v1/teachers/`、`GET /api/v1/classes/`、`GET /api/v1/subjects/`、`GET /api/v1/rooms/`、`GET /api/v1/time-slots/` |
| 排課需求總覽 | 顯示目前這學期設定了哪些 `ClassSubjectRequirement` | `GET /api/v1/class-subject-requirements/` |
| 排課控制台(核心亮點頁面) | 觸發 generate-lessons → run-scheduler,顯示進度與結果 | `POST /api/v1/schedule-versions/{id}/generate-lessons`、`POST /api/v1/schedule-versions/{id}/run-scheduler` |
| 課表檢視(核心亮點頁面) | 依 Class / Teacher / Room 三種視角查看排課結果 | `GET /api/v1/schedules/`(前端自行依 `class_id`/`teacher_id`/`room_id` 分組呈現) |
| 失敗診斷畫面(核心亮點頁面) | 排課失敗時,把 `lesson_failures`/`post_hoc_violations` 轉成人類看得懂的清單 | 沿用 `run-scheduler` 的失敗回應(422,含 `failure_type`) |

**失敗診斷畫面是整個前端最有價值的一頁。** 它直接把系統最花力氣打磨的 Explainable Scheduling——三種失敗類型(`DEFINITELY_INFEASIBLE`/`SEARCH_LIMIT_EXCEEDED`/`TIMEOUT`)、Task 23 的靜態可行性預檢機制——視覺化,呈現「為什麼排不出來、具體是哪個老師哪個限制、建議怎麼修」。這是一般排課工具做不到的差異化亮點,開發優先順序應該最高。

| 行政區塊呈現(午餐、課間活動、教師午會等不對應任何 `ClassSubjectRequirement` 的固定內容) | 本文件第 7 章「行政區塊」 |
| 響應式/行動裝置支援(桌面瀏覽器優先) | 純前端範圍決定,未記錄在其他文件(見本文件末尾的澄清事項) |

### 課表呈現方式的具體決定

課表呈現方式為**縱軸放節次(第幾節)、橫軸放星期一到五的表格**,只呈現排課引擎實際排定的課(國語、數學、自然這類一般科目課)。

**不呈現**午餐、課間活動、教師午會等行政性質的固定區塊。如果某個時段目前系統沒有排任何課,該格保持空白,不得為了畫面完整度而填入系統實際上沒有產生的內容。

這是刻意的範圍決定,不是遺漏。

## 4. 技術選型

| 項目 | 決定 | 理由 |
|---|---|---|
| 前端框架 | React + TypeScript + Vite | 沿用專案最初規格書既定選型 |
| 路由 | React Router | 業界標準,頁面數量少,學習成本低 |
| 狀態管理 | React 內建 `useState`/`useContext`,不用 Redux/Zustand | 頁面少、資料流簡單,不需要額外套件增加複雜度 |
| HTTP 呼叫 | axios(而非原生 fetch) | 已與使用者討論兩者取捨:fetch 可省一個 dependency,但此專案每個請求都要帶 JWT token、且需統一處理排課失敗時的結構化錯誤(`lesson_failures`/`post_hoc_violations`),axios 的攔截器(interceptor)可以統一處理「自動帶 token」與「錯誤格式轉換」,讓開發精力留給課表呈現、失敗診斷畫面等核心功能,經評估後使用者選擇 axios |
| UI 樣式 | Tailwind 或簡單 CSS module | 不追求精緻設計,這不是設計作品集,功能展示優先於視覺打磨 |
| Token 儲存 | `sessionStorage`(瀏覽器分頁關閉即清除) | 比 `localStorage` 稍微安全,對 demo 情境已足夠 |
| 部署方式 | 本機開發環境(localhost)優先 | 目前目標是面試/作品集展示,非正式上線給教務處使用;CORS 設定之後若要擴充到雲端部署,只需在後端 `main.py` 的允許來源清單新增一行,不需重新架構,兩者決策互不衝突 |

### 階段 A 開發時的擴充性要求(避免階段 B 需要重寫)

以下三點是**硬性約束**,不是可有可無的建議——階段 A 動手寫程式碼時就要照著做,否則階段 B 要做完整 CRUD 時,等於重寫階段 A 的程式碼。

**(a) API 呼叫層(axios 封裝)必須完整支援 GET/POST/PATCH/DELETE 所有方法**
現在要怎麼做:即使階段 A 只會呼叫 GET,封裝的 API client 介面(例如每個資源對應的 function 集合)一開始就要包含 `list`/`get`/`create`/`update`/`remove` 這五種操作的完整簽章,對應到後端每個資源既有的 CRUD endpoint,階段 A 只是「先不呼叫」`create`/`update`/`remove`,而不是「介面裡沒有」。
為什麼:如果呼叫層一開始就只針對唯讀場景簡化(例如只寫 `fetchTeachers()` 這種單一 GET function),階段 B 要補上編輯功能時,要重新設計整個呼叫層的介面形狀,而不是單純新增幾個 function。

**(b) 頁面版面必須預留操作按鈕的視覺空間與版面結構**
現在要怎麼做:基礎資料瀏覽頁的表格(以及其他之後會需要操作的清單頁面),排版時就要包含「編輯」「刪除」「新增」等操作按鈕的欄位/區塊,階段 A 這些按鈕可以不存在,或以停用(disabled)狀態呈現,但版面結構本身要先長成階段 B 完成後的樣子。
為什麼:表格欄位、按鈕留白這類版面決定,一旦其他樣式跟著目前的版面定案,之後插入新欄位往往牽動整個表格的寬度分配與響應式行為(即使本專案不做響應式,桌面版面本身的欄寬配置也一樣會被牽動),等到階段 B 才調整版面,等於重新設計一次頁面。

**(c) TypeScript 型別定義必須完整對照後端 Pydantic Schema 的全部欄位**
現在要怎麼做:每個資源的 `interface`(例如 `Teacher`、`ClassSubjectRequirement`)要包含後端對應 Schema(`TeacherRead`、`ClassSubjectRequirementRead` 等)定義的**全部**欄位,不是只定義階段 A 列表顯示會用到的欄位子集。
為什麼:型別定義是階段 B 表單驗證與型別安全的地基,如果階段 A 只定義顯示需要的欄位子集,階段 B 寫編輯表單時會發現型別缺欄位,回頭補型別本身是小事,但補齊過程中很容易發現「原本以為用不到的欄位,其實在某個顯示邏輯裡被隱式假設不存在」,反而製造出階段 A 遺留的隱藏 bug。

## 5. 核心使用者流程

### 流程 A:登入 → 瀏覽基礎資料

```
登入
  └─→ 看到 Dashboard(顯示這學期基本統計:幾個班級、幾位老師、幾筆排課需求)
```

### 流程 B:觸發排課(展示 CSP 求解能力,這是最重要的一條流程)

```
排課控制台
  └─→ 選擇 ScheduleVersion
        └─→ 按「展開課程清單」
              └─→ 顯示「共 X 堂課待排」
                    └─→ 按「開始自動排課」
                          └─→ 顯示 loading
                                ├─→ 成功 → 導向課表檢視,顯示剛排好的結果
                                └─→ 失敗 → 導向失敗診斷畫面,清楚列出每個問題
                                            (哪個老師、哪個限制、建議怎麼修)
```

### 流程 C:查看課表(展示成果)

```
課表檢視
  └─→ 切換「依班級」/「依教師」/「依教室」三種視角
        └─→ 用表格呈現(縱軸節次、橫軸星期),每格顯示科目+對象
```

## 6. 非功能需求

- **錯誤訊息必須忠實呈現後端內容**,不能為了畫面好看而簡化掉具體的失敗原因——這違背 Explainable Scheduling 的精神,是本專案的核心設計原則。
- **CORS**:後端 `main.py` 目前完全沒有設定 CORS,前端串接前需要補上。建議放進第一個前端 Task 一併處理,允許來源設為本機開發用的 Vite 預設 port。
- **不需要考慮**多語系、無障礙(a11y)等進階需求。

## 7. 待辦事項(已與使用者討論並記錄,非本次範圍)

### 階段 B:教務處日常操作所需的完整 CRUD

這個系統最終要讓教務處人員親自上手日常操作,所以以下功能不是「排除」,是「確定要做,但排在階段 A 之後」:

- **完整資料新增/編輯表單**:涵蓋 `School`、`Teacher`、`Class`、`Subject`、`Room`、`TimeSlot`、`TeacherSubject`、`TeacherAvailability`、`ClassSubjectRequirement` 共 9 張表(或子資源)的新增/編輯/刪除操作。除了表單本身,還需要前端表單驗證,以及把後端回傳的結構化錯誤(例如 `DuplicateValueError`/`InvalidReferenceError` 對應的 409/422 JSON)轉成更友善的中文錯誤提示——教務人員看不懂原始 JSON 錯誤訊息。
- **使用者/角色管理介面**:操作面向的功能(建立/停用帳號、指派角色),不是單純瀏覽。`STUDENT` 角色維持既有決定,仍刻意排除(專案最初重新評估規格時的決定,MVP 只做 `ADMIN`+`TEACHER` 兩種角色),這點不受本次階段調整影響。

**工作量提醒**:這個階段預估的工作量,量級上大約是階段 A 的 2.5–3 倍 Task 數量、3–4 倍開發時間(9 張表的表單 + 驗證 + 錯誤訊息轉換,遠比 6 個唯讀展示頁面繁重)——不需要精確數字,只需要理解這是份量明顯更大的一塊工作。因此列為「有餘裕再進行」,**不影響階段 A 的優先開發與驗收**。

### 其他待辦事項

1. **`ClassSubjectRequirement.fixed_time_slot_id`**:允許排課前手動指定某些課固定在特定時段(例如「地球公民課固定在星期三第三節」),排課引擎需跳過已固定的 Lesson、直接視為已排定。這是為了解決「部分課程時段固定」這個真實需求,採用下拉選單方式(非拖拉),範圍刻意縮小,不做成完整的 Fixed Lesson 系統。**建議在開始建立前端專案骨架之前,先完成這個小 Task**,因為它會影響「排課控制台」頁面設計需求時的表單欄位。
2. **行政區塊(午餐、課間活動、教師午會)**:不對應任何 `ClassSubjectRequirement`,需要更大的資料模型調整,列入未來規劃。
3. **拖拉互動介面(drag-and-drop)**:維持專案最初規格重新評估時的決定,有餘裕再做。
4. **完整進階排課規則庫**:包含 Fixed Lesson 全集、行政人員不排課、本土語三班同天上課、行政課程集中安排等規則,已在稍早的開發階段記錄為待辦,尚未排入。
